# 从零准备并实现一个个人学习助手

你最初提出的功能，可以拆成一条完整的学习流程：**确定章节 → 取得资料 → 整理知识 → 用例题与类比解释 → 自测 → 保存学习记录**。本项目已经把这条流程做成能在本机运行的网页。

## 一、开始写代码前准备什么

### 先明确输入和输出

“我学到第三章了”通常不够。不同教材的第三章可能讲不同内容，因此至少需要章节名称；要严格对应某一本书，就需要章节原文。

| 要准备的内容 | 最小可用版本怎么处理 |
| --- | --- |
| 课程与教材 | 用户填写，不猜测教材版次和目录 |
| 章节范围 | 输入明确标题，或选择已导入 PDF 的文件页序 |
| 原始资料 | PDF、截图、TXT / Markdown 或粘贴正文 |
| 学习偏好 | 理解原理、备考、实际应用；入门或有一定基础 |
| 输出格式 | 概览、目标、知识点、例题、生活类比、四选一自测 |
| 长期保存 | 章节内容、来源、笔记、作答、完成状态与追问 |

准备一份篇幅较短、自己能判断对错的材料作为首个样本。本项目的 `examples/计算机网络-网络层笔记.md` 可以用于走通流程；正式评估时应换成你实际使用的教材章节。

### 再准备运行环境

本项目的运行环境是 Python 3.11 或以上版本、一个现代浏览器，以及 Python 依赖。Windows 双击启动文件会创建项目自己的虚拟环境并安装依赖。普通使用不需要 Node.js，也不需要单独安装数据库服务。

整理新章节还需要一个模型服务：可以是远程服务，也可以是你已经在本机运行的兼容服务。本程序只负责调用它，不会自动下载模型。需要准备基础 API 地址、模型 ID，以及服务要求的 API 密钥；识别截图还要求模型支持图片输入。

先用短文本确认接口连通，再验证一整章。接口能连通与讲解是否准确，是两件需要分别检查的事情。

## 二、前端写什么

前端是浏览器里能看到和操作的部分。在本项目里：

- `dist/index.html`：布局、章节表单、模型设置表单和学习区域。
- `dist/styles.css`：字体、颜色、卡片、弹窗和不同屏幕宽度的布局。
- `dist/app.js`：按钮行为、接口请求、页面状态和错误处理。

重点不是先做很多页面，而是把一次学习过程接起来：

1. 新建章节，填写课程、教材、标题。
2. 选择资料模式或标题模式，必要时上传、预览并选页。
3. 提交后显示后台任务状态。
4. 成功后把结构化结果分别展示到知识点、例题、类比和自测标签页。
5. 支持来源跳转、追问、笔记保存和内容导出。

当章节积累起来，还需要按课程或标题搜索、按完成状态筛选，以及集中重做错题。资料导入可以读取 PDF 内嵌书签来辅助选章；书签的结束页是估算值，要让用户预览确认。备份页面先展示将新增、复制或跳过哪些记录，再合并恢复，避免覆盖已学内容。

前端需要同时考虑等待和失败。例如上传文件时禁用重复提交；模型失败时保留表单；切换章节前保存笔记；两个窗口同时写笔记时提示合并。

前端通过本机后端调用模型，因此模型密钥不需要出现在浏览器的生成请求里。只有配置服务时，网页才把用户输入的密钥提交给本机后端保存。

## 三、后端写什么

后端处理文件、调用模型、校验结果并保存数据。可以按四层阅读本项目：

| 层次 | 文件 | 处理的问题 |
| --- | --- | --- |
| 接口与任务 | `backend/main.py` | 收到什么请求，怎样提取资料，何时创建任务，怎样返回错误 |
| 数据格式 | `backend/models.py` | 用户输入与模型输出应该有哪些字段、哪些值有效 |
| 模型流程 | `backend/ai.py` | 提示词、长文本整理、HTTP 请求、结果校验与一次修正 |
| 存储 | `backend/storage.py` | 建表、读写事务、恢复章节与学习记录 |
| 学习备份 | `backend/backups.py` | 版本化格式校验、整批事务、冲突副本与重复导入去重 |

这一版只有一个本地服务，同时提供网页文件和接口。前后端使用同一个地址，部署与启动比较直接。

```mermaid
flowchart LR
    U[用户输入资料或章节标题] --> W[本地网页]
    W --> A[FastAPI 接口]
    A --> P[确定范围并组织提示词]
    P --> M[用户配置的模型服务]
    M --> V[结构与来源编号校验]
    V --> D[(SQLite 学习记录)]
    D --> W
    W --> N[自测、笔记、复习、导出]
    N --> A
```

模型负责生成讲解；文件选页、记录保存、正确选项的查验和页面展示由程序负责。把这些职责分开，模型服务临时不可用时，已经保存的章节仍然可以学习。

主要接口可以这样理解，详细字段以运行后的 `/api/docs` 为准：

| 动作 | 方法与路径 | 返回内容 |
| --- | --- | --- |
| 上传资料 | `POST /api/materials` | 资料 ID、页数、提取提醒、首页文字、可用的 PDF 书签 |
| 预览某一页 | `GET /api/materials/{id}/pages/{page}` | 该页提取文字 |
| 开始整理 | `POST /api/chapters/generate` | 生成任务 ID，HTTP 202 |
| 查看生成状态 | `GET /api/jobs/{id}` | 阶段、错误或已生成章节 ID |
| 读取章节 | `GET /api/chapters/{id}` | 内容、来源、笔记、作答与追问记录 |
| 保存笔记 | `PUT /api/chapters/{id}/notes` | 保存结果和新的笔记版本号 |
| 检查作答 | `POST /api/chapters/{id}/attempts` | 是否正确、正确选项与解析 |
| 章节追问 | `POST /api/chapters/{id}/questions` | 回答及消息 ID |
| 导出 | `GET /api/chapters/{id}/export` | Markdown 文件 |
| 打印讲义 | `GET /api/chapters/{id}/print` | 已保存整章的可打印页面，浏览器可另存为 PDF |
| 错题复习 | `GET /api/review` | 各章节最新一次答错的题目；重新提交后展示答案 |
| 学习备份 | `GET /api/backups/export` | 不含模型配置和密钥的 JSON 学习记录 |
| 恢复预览 | `POST /api/backups/preview` | 新增、冲突副本和跳过的数量及章节预览 |
| 合并恢复 | `POST /api/backups/import` | 整批导入结果，重复请求不会重复新增 |

例如，已配置模型后，按标题整理的请求主体是：

```json
{
  "course": "计算机网络",
  "textbook": "我正在使用的教材名称",
  "chapter": "第三章 数据链路层",
  "mode": "topic",
  "goal": "understand",
  "level": "beginner"
}
```

这个请求没有提供教材正文，所以结果必须标为通用讲解。把书名填进去，并不意味着程序已经获得或读取了那本书。

## 四、怎样让模型总结一章

### 第一步：明确材料的边界

资料模式先提取实际文字，按选定页序取得本章内容，再拆成较小片段。每个片段有稳定编号和来源标签，例如 `p12-s1` 对应文件第 12 页的第一个片段。

没有可读文字、选页越界或内容超限，都应在调用模型前提示用户。不能只取开头一部分，又把结果称为整章总结。

### 第二步：先整理结构，再组织讲解

短章节直接交给模型。长章节按片段分组，先提取各组的概念、公式、条件和易错点，保留来源编号，再汇总成统一结果。

总结要求应当具体：

- 核心概念是什么，彼此有什么关系？
- 哪些公式有使用条件，哪些概念容易混淆？
- 初学者需要哪些前置知识？
- 例题怎样逐步推导，哪里容易做错？
- 生活中的什么场景有助于理解，对应关系是什么，哪里不能类比？

例如把路由器比作路口指路牌，可以帮助理解“根据目的地选择下一跳”，但不能由此推断 IP 保证送达。类比的局限需要和类比一起写出来。

### 第三步：让输出成为数据

如果只让模型返回一大段文章，前端很难独立展示习题、隐藏答案或跳转来源。这里要求模型输出 JSON，后端用 `StudyGuide` 检查结构。

知识点条目的简化形状如下；完整定义见 `backend/models.py`：

```json
{
  "title": "最长前缀匹配",
  "explanation": "在多条匹配路由中，优先采用前缀最长的一条。",
  "key_takeaway": "先判断是否匹配，再比较前缀长度。",
  "pitfalls": ["不要认为默认路由总是优先。"],
  "source_ids": ["p12-s1"]
}
```

示例中的来源编号只是说明数据形状，实际生成必须使用本次导入确实存在的编号。

### 第四步：区分格式正确与知识正确

代码能自动检查字段是否齐全、选择题是否有四个不同选项、答案序号是否越界、来源编号是否存在。失败后要求模型修正一次，仍失败则不保存为成功章节。

这些检查不能证明数学推导正确，也不能证明引用原文确实支持结论。评估实际总结质量时，可以用下面这份检查表：

| 检查点 | 应该怎样验证 |
| --- | --- |
| 覆盖范围 | 对照章节目录，确认主要小节没有遗漏 |
| 定义与条件 | 对照原文，检查概念、前提、公式适用范围 |
| 来源 | 点击来源，确认原文真正支持知识点 |
| 例题 | 自己重新计算，检查步骤和答案 |
| 自测 | 确认只有一个正确答案，错误选项有明确理由 |
| 类比 | 检查对应关系与局限，避免类比造成新误解 |
| 诚实性 | 标题模式不冒充教材原文，原创题不冒充教材原题 |

可以固定选取三个实际章节：概念密集的一章、计算题较多的一章、公式或表格较多的一章。保留原文、生成结果和人工检查记录，修改提示词后使用同一批材料比较，才容易判断是否真的变好。

## 五、推荐的实现顺序

如果从空项目重新实现，建议按可验证的结果推进：

1. **先显示一份固定示例。** 验证学习内容的结构和阅读体验。
2. **接通前后端。** 能保存并重新读取一章，关闭程序后数据仍在。
3. **加入一种模型输入。** 先用标题或短文本生成完整内容。
4. **加入导入和来源。** 处理 PDF 选页、截图和长文本。
5. **补学习闭环。** 自测、追问、笔记、完成标记和导出。
6. **验证失败路径。** 密钥错误、服务限流、资料损坏、生成格式错误、进程中断和多窗口冲突。

本项目已完成上述流程与程序层面的验证。真实教材的教学质量还需要接通你选择的模型后，用实际章节按前面的检查表验收。

下一步看代码时，可以从 `dist/app.js` 的生成请求读起，跟到 `main.py` 的 `generate`、`ai.py` 的 `generate_guide`，最后看 `storage.py` 如何保存，再回到前端的章节渲染。这样能沿着一次实际操作理解整个程序。
